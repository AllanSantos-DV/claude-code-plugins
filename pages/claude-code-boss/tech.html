Daemon HTTP único ADR-001

O brain-server roda como um único daemon HTTP de longa duração (StreamableHTTP, stateful) numa porta fixa (38217), compartilhado por toda sessão do Claude Code e qualquer outro consumidor na máquina — um modelo, um SQLite. O .mcp.json usa "type":"http" direto (sem spawn por sessão).

sessão 1▸ sessão 2▸ sessão N▸ daemon único :38217▸ 1 modelo · 1 SQLite

Garantia + lifecycle

  • Auto-start + auto-upgrade: o hook brain-daemon-ensure.js (SessionStart/UserPromptSubmit) encontra-ou-inicia o daemon; a cada atualização do plugin, troca um daemon obsoleto pelo novo (lock em DATA_DIR + checagem de versão via /health). Desligue com BRAIN_HTTP_AUTOSTART=0.
  • Auto-setup em background: se o node_modules está faltando, o hook roda plugin-setup.js em background (detached, non-blocking) antes de tentar o spawn — sem bloquear a sessão e sem exigir intervenção.
  • Fail-open: qualquer erro só adia a disponibilidade da KB; o próximo SessionStart/UserPromptSubmit re-emite o ensure. Nunca bloqueia o início de sessão.
  • Endpoints: /health (aberto), /mcp (guarda de Origin), /shutdown (exige token local em <DATA_DIR>/brain-http.token ou BRAIN_HTTP_TOKEN).
  • Limites: MAX_BODY_BYTES = 1MB (proteção contra OOM), MAX_SESSIONS = 50 (prevenção de exaustão de FDs); graceful shutdown sem process.exit() hard kill.
Consumo externo: qualquer ferramenta (ex.: OpenCode) aponte para http://127.0.0.1:38217/mcp com project explícito. O parâmetro project é obrigatório por chamada — sem ele, o daemon rejeita (PROJECT_REQUIRED).

Hooks pipeline hooks servidos pelo daemon

Todos os hooks vivem em hooks/hooks.json. Desde a v2.28.0, cada evento tem um dispatcher in-process (lê o payload uma vez, roda cada run(event) concorrente, com timeout próprio, e funde o resultado). Na v3.0.0 (ADR-015) 13 hooks nem sobem processo: o hooks.json declara um mcp_tool hook_<nome> do brain-server, que roda o mesmo script in-process no daemon HTTP compartilhado — 8,9 ms p50 por hook (antes 122 ms com spawn). Ficam como command só os que precisam funcionar sem o daemon: SessionStart, o user-prompt-submit-dispatcher (que inclui o model-router-ensure) e o dashboard-command do /dashboard. Uma exceção na tool vira systemMessage de degradação (fail-open visível); Stop e os hooks de efeito colateral rodam num worker próprio, e cada hook tem prazo interno de timeout − 1 s.

Config & perfis

Um único eixo de enforcement, três modos — lido do config shipped mesclado com DATA_DIR/hooks/user-config.json (update-safe, sobrevive ao auto-update).

default

standard

Silencioso, mas aprende: só a curadoria dá 1 aviso soft e relenta. correction-detect fica LIGADO (nudge silencioso). Ficam desligados os nudges interruptivos e ferramentas de dev. session-summary (1×/sessão) e o retrieval continuam.

para quem estende o plugin

dev

Tudo ligado — curadoria escala até 3×; nudges, decisões, self-review, pesquisa, retros, auto-continue.

sem enforcement

free

Passa tudo: o Stop-dispatcher faz short-circuit e nada bloqueia; só o retrieval de contexto no prompt (read-only) segue ativo.

Backends do Brain

  • local (padrão): SQLite no DATA_DIR/brain/<projeto>/brain.db — zero servidor externo. Tem memória, recall, lições, curadoria e políticas. Não tem as tools que só o servidor entrega: grafo de código (graph_*), recall em dois níveis (compose_recall), ingestão de conversa e migração.
  • mcp-memory (integrado): o mesmo plugin passa a usar o servidor de memória (native-java) e ganha essas ferramentas. HTTP com auto-discovery via ~/.mcp-memory/run/daemon.json; ingestão opt-in; Migrar agora leva o acervo local para o servidor projeto a projeto (idempotente, fail-loud).
  • O agente ativa para você: no backend local o agente é avisado do que está desligado. Ele pergunta se você já roda um servidor em outro host (aponta para o endereço, sem instalar nada); se você não souber, reaproveita o servidor que já roda na máquina (instalado por plugins irmãos — nunca um segundo) ou o instala: backend_status, backend_setup (confere Java 21+ e dá o comando de instalação do seu sistema se faltar), backend_setup_status. Ele mostra a versão do servidor e atualiza só com o seu OK (backend_update). Pelo Dashboard, o mesmo assistente roda no botão Activate Server.
  • Auto-update HTTP: no SessionStart, consulta check_update no máximo uma vez por 24h e chama update uma vez, sem retry, sob lock cross-process. Um serverUrl remoto exige autoUpdate.allowRemote=true e nunca usa o fallback local. Se a nova versão falha no boot, o caminho local restaura o JAR anterior e confirma a versão restaurada em /health.version antes de reportar rollback concluído.
  • Backup: o Dashboard (aba Brain) guarda tudo o que o plugin aprendeu num .tar.gz (bancos SQLite em snapshot VACUUM INTO, sem modelos nem segredos) e restaura em outra máquina, com cópia de segurança antes. Os dados do servidor entram quando ele oferecer backup_export/backup_import (contrato em docs/BACKUP-CONTRACT.md).
  • Status em tempo real (scripts/brain-status.js, hook no UserPromptSubmit e comando /brain-status): reporta mode, connected, project, backend, details (URL/transporte/JAR) e latency — mesmo contrato exposto em GET /api/brain/health e refletido no badge online/offline do Dashboard.

Identidade do projeto (recall entre máquinas/pastas)

Precedência: CCB_PROJECT_ID (env) → .memory/project.json (viaja com a pasta) → .claude-boss-project (legado) → git remote origin (host/owner/repo, o mesmo em qualquer máquina ou caminho). Sem id, a memória fica desligada na pasta: o agente examina a pasta, lista os projetos que já existem (project_list), pergunta se é um projeto novo ou a continuação de um existente e grava com project_set (nome repetido exige confirmação).

Model Router Anthropic + OpenAI

Custom upstream e BYOK aceitam Anthropic Messages ou OpenAI Chat Completions. Você escolhe URLs completas e independentes para catálogo de modelos, geração, contagem de tokens e classificação pelo dashboard, por user-config.json ou por variáveis de ambiente.

custom upstream

Credencial da assinatura preservada

O router leva a rota do Claude Code ao gateway escolhido e encaminha somente os headers extras autorizados.

BYOK

Só a sua chave segue para o endpoint

O token da assinatura é removido. O destino recebe apenas os headers configurados por você.

Adaptação OpenAI e catálogo isolado

  • Picker: modelos não Anthropic recebem o alias anthropic-ccb-alias- na listagem e voltam ao ID real antes da geração ou contagem.
  • Conversão: mensagens, imagens base64 suportadas, ferramentas, tool results, respostas JSON e stop reasons atravessam o adapter nos dois sentidos. No streaming SSE, fragmentos sucessivos do nome de uma tool call são concatenados, e o usage recebido sozinho no chunk final é preservado no fechamento do stream.
  • Isolamento: o catálogo dinâmico é separado por tenant, destino, protocolo e fingerprint de credenciais; modelos de um gateway não aparecem em outro.
  • Precedência: dashboard/user-config.json → ambiente → defaults. Campos incompatíveis falham explicitamente, sem omissão silenciosa.

Mapeamento de modelo do BYOK (origem → destino) · v3.0.0

  • Escopo: opcional e vazio por padrão. byok.modelMap troca o model enviado ao endpoint só na rota BYOK (always, fallback on-limit e cooldown), em geração, classificação remota e count_tokens. O caminho da assinatura nunca é alterado e o corpo original não é mutado: o mapeamento trabalha sobre uma cópia, depois da tradução de protocolo, em Anthropic e OpenAI.
  • Correspondência: ID exato; depois o ID sem data de snapshot (-AAAAMMDD); depois padrões com * (o mais específico vence, empate pela ordem de inserção). Sem prefixo implícito: claude-opus-5 nunca captura claude-opus-5-5. Sem regra, o model segue como veio.
  • Injeção: byok.modelInjection (desligado por padrão) grava o modelo resolvido em campos extras do corpo ou em headers via template {model}, o único placeholder; nada é avaliado como código. Não pode alterar model nem headers de credencial/protocolo.
  • Dashboard: editor de regras em /dashboard → BYOK, com destinos sugeridos pelo /v1/models do endpoint ou digitação livre. Regra inválida é recusada com 400 e não chega ao disco.
  • Fail-loud: regra inválida no fallback responde com a causa em vez de ceder à NVIDIA; em always vira 502 proxy_error. Erros do endpoint citam o modelo enviado e a regra aplicada.
